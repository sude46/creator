## 2 安全边界

### 2.1 身份与数据权限

- 前端不可信，ownerId、角色、状态、处理代次和文件元信息不能直接成为服务端事实。写入采用字段白名单，用户身份来自已验证 Actor。
- 更新和删除按 `id + owner_id + version + 业务状态` 条件写入，不能只在读取时校验所有权。管理员通过独立用例授权并记录原因。
- 首页、搜索、收藏、详情、封面和播放授权都检查同一可见性。不能只保护视频播放而从封面地址、导出或收藏泄漏私有内容。
- 视频原文件和封面桶均私有；原文件、封面等资源不能按“知道对象键即可访问”的方式公开。
- 原始密码、密码哈希、Cookie、CSRF token、存储凭据和完整签名 URL 不写业务日志。注册 DTO 的字符串表示已隐藏密码，认证凭据类型已隐藏哈希。
- ID 字符串格式和 UUID 对象键只能降低猜测便利性，不能代替鉴权。

### 2.2 登录与 Session

当前按来源 IP 的有界窗口限制请求数量，另已增加每 API 实例的认证计算并发上限，注册、登录和管理员初始化共享预算；默认并发 2，超额立即返回 429 和 Retry-After，不占用 Tomcat 线程排队等待。

该准入通过包装实际 DaoAuthenticationProvider 实现，覆盖真实 AuthenticationManager 调用及未知用户名的防计时攻击哈希，保留 Spring 密码验证流程；注册/初始化在同一预算内计算哈希。AuthenticationManager 明确使用单个 ProviderManager，避免父子管理器失败回退导致重复密码计算。配置在部署前按 CPU 和 BCrypt 耗时实测选择，不能为了提高吞吐降低哈希强度。不要新增全局账号锁定，让攻击者仅凭用户名永久锁住他人账号。

RegisterUser 与 BootstrapAdmin 已移除包裹 BCrypt 的外层事务，规范化、校验与哈希在事务外执行；最终创建只有一条 INSERT，使用数据库语句原子性和唯一索引保证一致性，无需额外长事务。管理员初始化的并发重名仍依赖唯一约束，不覆盖既有凭据。集成测试在实际编码器调用时断言没有活跃数据库事务。

登录凭据已在进入用户查询和昂贵计算前限制用户名长度、密码字符数及 BCrypt 72 字节范围，保证注册与认证对密码字节边界的理解一致。该检查属于凭据输入边界，不把完整的新密码强度规则强加到未来迁移进来的旧账号上。代理和请求解析层的总请求大小限制仍需在部署模块落实。

Session 保持 HttpOnly、SameSite，生产强制 Secure 和 HTTPS；登录轮换会话 ID，写请求保留 CSRF。未登录访问 CSRF 接口也可能创建 Session，生产应在边缘限制该入口访问频率，并给会话数量与 JVM 堆设置容量上限和监测，不能认为只给登录加限流就覆盖了内存消耗。

2026-11-23 增加数据库设备会话注册表：登录成功后在 `user_session` 登记随机会话行，数据库只保存 JSESSIONID 的 SHA-256 哈希，不保存原始 Session ID；受保护请求校验账号状态、设备行、会话哈希、过期时间和 `user_account.session_version`。账号安全页可列出未撤销/未过期设备，支持单设备退出、退出其他设备和退出全部设备。修改密码和超级管理员重置密码会在同一事务递增目标账号 `session_version` 并撤销全部目标会话，当前设备也在下一次请求失效。设备会话默认空闲 30 分钟过期，与 Servlet Session 超时一致；撤销/过期行目前只做逻辑过滤，未实现定时物理清理。当前部署是单 API 实例；多实例需要粘性会话或 Spring Session，数据库注册表不能复制内存 HttpSession。设备列表展示请求 IP 和 User-Agent，反向代理后必须正确配置受信转发头，不提供地理定位或设备指纹。

每个受保护请求查询一次不含哈希的账号摘要和设备会话，是为了下一次请求及时感知禁用、角色变化和会话撤销。首版保留这个一致性选择；不能直接加入长 TTL 缓存使账号禁用或退出设备悄悄延迟生效。引入缓存时必须先定义失效通知和允许的延迟窗口。

### 2.3 受信代理与响应

- 本地直接访问和生产 Nginx 使用不同配置。仅当请求来自明确的反向代理时才解析转发地址，不能盲目信任客户端 X-Forwarded-For。
- 生产由 Nginx 做连接/速率准入，应用继续做业务限流；开发代理下共享 IP 配额的限制已写入 README。
- 保留 Spring Security 默认的安全响应头，生产增加经页面验证的 CSP、Referrer-Policy 和 HTTPS 下的 HSTS。CSP 要兼容实际组件样式、媒体域和播放器，不直接复制会使页面失效的模板。
- 登录和签名授权响应禁止共享缓存。对象存储签名媒体使用与私有访问一致的缓存规则，CDN 不能忽略签名参数缓存私有内容。
- Cookie、令牌及签名 URL 不进入错误响应或 URL 路径参数；错误关联用 requestId。代理访问日志避免记录含签名凭据的完整查询串。

## 3 上传与媒体处理

### 3.1 在解析文件之前限制资源

仅在 Controller 内检查文件大小太晚：Servlet multipart 可能已经解析并写临时文件，缺失 CSRF header 时安全组件读取表单参数也可能触发解析。

首版已改用原始 video/mp4 请求体并关闭自动 multipart 解析，上传链路为：

```text
边缘大小/连接/速率限制（部署时落实）
→ 恢复认证上下文
→ 账号检查与上传请求类型/CSRF header 存在性检查
→ 上传并发及临时磁盘预算准入
→ Spring Security 校验真实 CSRF token
→ 业务所有权/版本/状态及配额检查，持久化上传凭据
→ 受控临时文件、文件头初筛与真实接收字节校验
→ 对象写入
→ 短事务再次校验并绑定
```

上传过滤器已接入 CsrfFilter 之前、账号有效性过滤器之后；缺身份、缺/错 CSRF 和越权的请求有 body 未读测试。另有真实嵌入式 Tomcat HTTP 上传测试。测试证明当前顺序及请求契约，不等于生产代理/慢网都已验证；不能只检测“有 header”就放行。

首版采用单 API，已实现默认实例全局上传并发 2、每账号 1；准入无长等待队列，结束或失败在 finally 释放。这是单实例的 HTTP/临时磁盘准入保证；数据库绑定配额另在账号行锁内保证，未来扩容仍需共享上传准入。

已实现默认 200 MiB 文件上限，原始请求体只含一个文件，元信息在独立 JSON 草稿接口维护，不接受 multipart。Content-Length 用于初筛，实际复制时仍累计字节并校验声明长度。临时文件写入独立配置目录，磁盘检查为低水位 + 在途最大文件体积预留；操作系统目录隔离、配额和反向代理请求大小仍需部署时落实。

接收循环预算默认 120 秒，每个读块后检查，嵌入式 Tomcat 上传读取空闲超时设为 15 秒，末次阻塞可能额外消耗空闲预算；不是精确 120 秒硬截止。存储 HTTP 建连/读写及跨分片整体预算独立设置。磁盘阻塞、慢网边界及代理总时限还需实测；客户端中断、读取超时、达到字节限制均走临时文件清理和持久化凭据补偿路径。

### 3.2 配额与磁盘预算

首版已实现单用户默认 1 GiB 已绑定源文件逻辑配额、5 个待处理源文件上限、5 条未回收凭据上限及临时磁盘低水位拒绝。最终绑定在账号行锁内重新读取配额并写入，两独立线程竞争有测试；不是无锁的“先 SUM 再插入”。未回收凭据包括清理失败仍处于 CLEANING 的记录，不因删除失败释放名额。默认值是候选配置，真实资源和 MySQL 行为待验证。

当前逻辑配额保守统计全部已绑定源文件，尚未实现删除后释放；未绑定对象受凭据数量约束。未来逻辑配额释放与物理回收是不同时间点。宽限期、孤立对象及未完成分片也会占空间；API 临时磁盘低水位不代表远端 MinIO 容量充足，存储自身容量与告警需部署验证。桶要求版本化 OFF；未完成分片由 `STORAGE_INCOMPLETE_UPLOAD_CLEANUP` 选择依赖 MinIO 服务端过期清理或强制校验 S3 bucket lifecycle，具体设置见 [上传接入说明](upload-storage-setup.md)。

临时目录预算至少按下式估算，再用实测峰值校正：

```text
并发上传数 × 单文件上限
+ Worker 并发 × 每任务源文件及产物预算
+ 崩溃残留与安全余量
```

例如上传并发 2、文件上限 200 MiB、Worker 并发 1 且按每任务 400 MiB 预算，基础临时占用约 800 MiB，尚未包括安全余量、数据库和长期对象存储。这个例子不能用来直接确定服务器总磁盘。

### 3.3 不可信媒体的隔离

- 扩展名/MIME/文件头初筛后，以 FFprobe 实际探测为准；明确允许容器、视频编码、音频编码、像素格式、时长、分辨率和音轨数量。
- 固定可执行文件和参数数组，只传受控临时文件路径。不要拼 shell、接受用户提供的 FFmpeg 选项、任意输入 URL 或任意输出路径。
- 输入协议采用严格允许列表，禁止网络协议和外部引用扩展；不启用 MP4 外部数据引用等能力。只限制文件名不能防止媒体容器诱导外部访问。
- Worker 使用低权限账户、最小目录挂载与资源预算；FFmpeg 子进程可读范围尽量局限当前任务目录，不能读取数据库配置、云凭据和其他用户文件。
- 子进程环境变量采用必要项允许列表，不直接继承数据库和存储凭据。仅使用非 root 账号或协议允许列表不等于完整沙箱；文件系统、进程与网络隔离机制要在实际部署环境验证，不能据此宣称可防御所有解析器漏洞，也不为启动隔离任务向 Worker 开放宿主 Docker 管理套接字。
- 分别限制探测时间、截图时间、输出文件大小和 stdout/stderr 收集量；异常输出不能无限写入内存或日志。超时终止进程树，等待退出后清理目录。
- 首版 Worker 并发 1、prefetch 1，FFmpeg 线程数明确限制。API 进程不执行 FFmpeg，不能通过 Spring 无界异步线程池把排队转移到 JVM。
- 维护 FFmpeg、JDK、数据库和存储依赖的版本记录与更新检查。已固定版本不等于长期安全；部署时检查镜像维护状态并在升级后回归。

初始超时可从 FFprobe 15 秒、截图 45 秒、任务整体 300 秒、执行租约 360 秒开始测试；它们是候选值而非已验证配置。任务整体预算包含拉取和上传，不应只计算 FFmpeg 运行时间。

## 4 API 与数据库性能

### 4.1 明确读写成本

| 链路 | 首版查询原则 | 防止的问题 |
| --- | --- | --- |
| 账号有效性 | 一次唯一索引摘要查询，不读密码哈希 | 重复查库及无必要敏感字段读取 |
| 视频列表 | SQL 内过滤、稳定排序、有限页大小 | 查全表后过滤导致泄漏和错误分页 |
| 收藏列表 | 分页查询并批量获得可见性/摘要 | 每条收藏再查作者、视频、封面造成 N+1 |
| 视频详情 | 有限次主键/关联查询，授权后按需签名 | 序列化过程中隐式查库或调用存储 |
| 待审列表 | 状态索引与限定页大小 | 扫全表、一次返回全部待审作品 |
| 处理状态 | 多作品批量查询、复用当前 Actor | 每个卡片独立轮询并重复账号查询 |
| 导出 | 限制总行数，超过上限拒绝或分批 | 无界读内存、长期占用连接 |

首版列表默认 20 条、上限 50 条作为候选值。列表封面按当前页签名，不同时签所有历史作品；S3 兼容本地签名实现不应为了每个卡片额外 HEAD 对象。资源是否可用使用已记录的状态，后台做必要核对。

首页先用偏移分页，限制最大偏移；数据变大后按 publishedAt 和 id 做游标分页。中文标题 `%关键词%` LIKE 不能靠普通 B-tree 解决性能问题，先限定输入与数据规模并测量，再决定全文索引或外部搜索。

索引依据真实 SQL、过滤选择性和排序设计，使用 EXPLAIN 验证。不要给每个字段建索引，也不要把所有状态盲目拼成巨型联合索引。count 查询如成为瓶颈，可调整“是否还有下一页”的分页契约，不优先缓存错误的总数。

### 4.2 事务与连接池

密码哈希、对象上传、消息发布与确认、FFmpeg 均不持有业务数据库锁。需要数据库原子性的记录使用短事务；作品、任务、资源保持固定锁顺序。

连接池、HTTP 线程池和 SDK 连接池都配置容量、获取等待上限、连接/读取超时。数据库不可用时尽快返回 503，不能将无限等待转化为堆积请求。SDK 超时和重试总时间必须纳入请求/任务整体预算，避免每层重试相乘。

API 8、Worker 2 条连接和 5 秒连接等待已作为默认 Hikari 配置应用，仍需用真实 MySQL 与压测校准，并为迁移和运维留出余量。总连接约束为所有实例池上限之和加维护连接不超过数据库可用连接数。API 和 Worker 同库并不意味着它们应该共享同一进程连接池。

死锁只能对明确、幂等的短事务做有界重试，不能把含对象写入的整条上传链路盲目重放。数据库提交结果未知时，通过请求键/资源绑定状态确认，不能简单当作失败补偿删除。

### 4.3 轮询和浏览器请求

前端状态轮询初始 3～5 秒，加少量随机抖动；隐藏页面暂停、离开页面取消、连续失败退避到更长间隔。按作品 ID 集合批量请求，处理完成后停止，不额外引入 WebSocket。

例如 100 个活跃创作页面每 5 秒轮询一次，约产生 20 次轮询请求/秒，尚未计入每次请求的 SQL 数。这个计算用于评估方案，不能当作平台已支持 100 并发的证据。

视频字节通过签名媒体地址和支持 Range 的媒体入口传输，不经过 Controller 把整个文件读入 byte[]。经 Nginx 转发时仍消耗服务器带宽和连接数，只是避免占用 API 的 Java 线程、堆和业务连接池；公网带宽往往先于业务 SQL 成为瓶颈。

## 5 RabbitMQ 与任务调度的容量

- 数据库待派发和到期恢复使用索引与有限批次，初始每批 50 条测试；无任务时拉长间隔，避免固定毫秒轮询数据库。不能一次把所有待处理任务读进内存。
- 派发器只保持有限数量未确认消息，confirm/return 有截止时间和可关联的派发令牌；连接故障时退避，不用忙循环。
- 队列设置容量策略；需要保留任务时使用拒绝新发布并让数据库稍后重投的语义，不使用静默丢弃旧任务的 overflow 行为。消息体有大小上限和版本校验。
- Worker prefetch 与并发保持一致的小值。重试有总次数、退避和随机抖动，永久错误不重试；消息非法转死信，死信有保留与排查规则，不能无限增长。
- 队列长度不是唯一指标，同时监测数据库待处理量、最老任务年龄、租约到期数、失败率。MQ 空了不代表任务全部成功，MQ 有消息也不代表数据库有合法任务。
- 限制每用户待处理作品数量和上传准入，让容量控制尽量发生在保存大文件之前。排队等待过长要提示等待并触发运维观察，不通过无限增加消费者掩盖 CPU/磁盘不足。
- MQ、MySQL 或存储故障恢复时分批处理积压，避免同时重放所有任务形成恢复高峰。

## 6 部署与运维基线

当前 Compose 用于本地依赖，不应直接宣称已经是生产部署方案。生产至少完成：

1. 仅公开 HTTPS 入口和受限 SSH，数据库、MQ 管理台、对象存储控制台在私网或受控访问范围。媒体数据入口和管理入口分离。
2. 应用账号按最小数据库权限配置；生产区分迁移账号与运行账号，运行账号不持有建表/授权等运维权限。不同服务使用独立凭据并支持轮换。
3. 容器/进程配置内存、CPU、进程数和可写目录边界，应用与 Worker 以非 root 运行。不能用 Docker 的无限制默认值代替资源规划。
4. JVM 堆之外为直接内存、线程栈、元空间和本地进程留出空间。Worker 中 FFmpeg 不计入 Java 堆；限制容器内存时必须计入它。
5. 日志轮转、临时文件清理、对象存储与数据库磁盘水位告警，避免日志或死信占满系统盘。
6. MySQL、媒体文件和必要配置分别备份，至少做一次恢复演练；备份存储不能只有同机同盘副本，验证一致性和可恢复时间。
7. 健康检查区分进程存活与依赖就绪，运维指标和详细健康信息不公开；依赖未就绪时不要把 API 标记为可服务。
8. 锁定经验证的版本/镜像摘要并记录检查时间，升级先在本地回归。服务器无外网时准备镜像、依赖和产物清单及校验值。

具体资源数值先根据电脑与服务器配置确定。没有环境数据前不承诺所有基础设施能在某个固定内存规格下稳定共存。

## 7 可观测性与验收

至少记录 API 路由级耗时和错误率、数据库池活动/等待、SQL 慢查询、登录/上传拒绝数、任务等待/执行耗时、重试/租约恢复、FFmpeg 超时、临时磁盘与对象存储用量。指标按路由模板聚合，不按 userId、videoId、完整 URL 等高基数字段打标签；具体任务通过结构化日志关联 requestId/taskId。

尚未接入指标采集时不创建空监控组件。可先用日志与本地测量建立基线，再在部署模块接入必要指标端点并限制访问。

### 7.1 测试分工

| 验收项 | 测试方法 | 通过标准 |
| --- | --- | --- |
| 越权与数据泄漏 | A/B 用户和管理员覆盖所有读写入口 | 未授权不能获取资源、修改状态或看到私有字段 |
| 上传准入 | 缺 CSRF、大文件、低速输入、并发与中断 | 尽早拒绝，临时文件与并发许可最终释放 |
| 媒体隔离 | 伪格式、损坏媒体、外部引用、超时和异常输出 | 无任意网络/路径访问，无无限进程/日志/临时文件 |
| 并发一致性 | 真 MySQL 独立连接协调竞争 | 审核、绑定、任务结果与唯一约束只产生合法结果 |
| 资源耗尽 | 连接池满、磁盘低水位、队列容量达到上限 | 有界等待或拒绝，核心查询不被持续拖死 |
| 故障恢复 | Worker 强停、MQ/存储/数据库不可用后恢复 | 无错误发布，任务可追踪并最终进入明确状态 |
| 媒体播放 | Range 拖动、签名过期、下架、浏览器兼容 | 正常播放，新授权遵守状态，旧链接期限限制有记录 |
| 备份恢复 | 还原数据库与媒体对象，检查关联 | 能复现演示链路，恢复缺口和耗时有记录 |

### 7.2 性能基线计划

先记录机器规格、JDK、容器限制、数据量、带宽和测试脚本，再报告结果。候选读接口场景：1 万作品、10 万收藏，20 并发持续 5 分钟，分别测首页、搜索、详情、收藏；业务读接口 p95 低于 500ms 可作为初始验收目标，不是已达到的承诺。错误率需区分功能失败、预期 429 与容量过载。

再做混合场景：上述读取 + 2 个上传 + 1 个媒体处理，观察 API p95、CPU、堆、连接池、临时磁盘和任务等待。上传总耗时受带宽影响，视频首帧和拖动体验单独测试，不能将它们混入普通 API 的 500ms 目标。

如果目标未达成，先定位慢 SQL、N+1、连接等待、CPU 哈希/解码、磁盘或带宽，再选择优化。增加线程和连接可能扩大争用，必须比较优化前后相同负载的结果。

## 8 后续优化的触发条件

| 优化 | 需要先取得的证据 | 必须同时处理 |
| --- | --- | --- |
| Redis 共享 Session/限流 | 明确需要多个 API 实例 | 会话失效、限流一致性、Redis 故障语义 |
| 查询缓存 | 热点查询占主要数据库耗时且数据允许短暂陈旧 | 审核/下架失效、账号禁用、缓存穿透与重建 |
| 多 Worker | 队列等待持续超过目标且有额外 CPU/磁盘预算 | 租约、幂等、池与存储预算、恢复高峰 |
| 对象存储直传 | 大文件或慢网显著占用 API 上传连接 | 上传凭证范围、完成确认、对象校验、孤立清理 |
| 更好的中文搜索 | LIKE 实测或匹配质量不满足目标 | 分词、同步延迟、公开状态过滤 |
| CDN/媒体网关 | 带宽成本或播放延迟成为主要瓶颈 | 私有鉴权、缓存键、下架撤销与签名过期 |

当前优先执行顺序：账号计算与事务边界加固 → 上传准入与磁盘预算 → Worker 隔离和任务容量 → 查询索引与混合负载测试 → 生产部署和恢复演练。以上随对应模块逐次实现、测试、独立提交并推送 GitHub。
